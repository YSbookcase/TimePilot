# 병합 복원 정책

영문 에이전트용 문서: `docs/features/RESTORE_MERGE_POLICY.md`.

## 1. 목표

TimePilot의 현재 전체 복원은 백업 파일의 `timepilot.db`와 설정 파일로 현재 데이터를 대체한다.

병합 복원은 전체 복원과 다르다. 사용자가 백업 시점으로 돌아가고 싶지만, 백업 이후 현재 PC에서 쌓인 기록까지 잃고 싶지 않을 때를 위한 기능이다.

이 문서는 병합 복원 구현 전에 앱, 분류, 설정, 기록을 어떻게 매핑할지 정리한다.

---

## 2. 복원 방식 구분

### 전체 복원

- 백업 DB와 설정 파일로 현재 DB와 설정 파일을 대체한다.
- 가장 빠르고 단순한 복원 방식이다.
- 백업 이후 현재 DB에 쌓인 앱, 기록, 분류 변경, 설정 변경은 사라질 수 있다.
- 앱 목록도 백업 시점의 상태로 줄어들 수 있다.

### 백업 기준 복원 + 이후 기록 보존

- 백업 DB를 기준 데이터로 사용한다.
- 현재 DB에서 백업과 겹치지 않는 이후 기록을 추출한다.
- 추출한 기록을 백업 DB의 앱 ID와 분류 ID 체계에 맞춰 추가한다.
- 백업에 없는 앱은 백업 DB에 새 앱으로 추가한다.
- 사용자가 "백업 상태로 돌아가되 이후 기록은 보존"하기를 기대할 때 적합하다.

### 현재 데이터 기준 가져오기

- 현재 DB를 기준 데이터로 사용한다.
- 백업 DB에서 현재 DB와 겹치지 않는 기록을 추출한다.
- 추출한 기록을 현재 DB의 앱 ID와 분류 ID 체계에 맞춰 추가한다.
- 현재 설정과 현재 앱/분류 상태를 유지하려는 경우에 적합하다.

---

## 3. 매핑 방향

병합 복원은 기준 DB와 가져올 DB의 방향이 중요하다.

```text
백업 기준 복원 + 이후 기록 보존
baseline = backup
candidate = current
```

```text
현재 데이터 기준 가져오기
baseline = current
candidate = backup
```

`candidate`의 기록이 `baseline`과 시간상 겹치면 가져오지 않는다.

현재 구간 비교 로직은 다음 규칙을 사용한다.

```text
candidate.StartedAt < baseline.EndedAt
&& candidate.EndedAt > baseline.StartedAt
```

끝과 시작이 정확히 맞닿는 구간은 겹침으로 보지 않는다.

---

## 4. 앱 매칭 정책

1차 앱 매칭은 보수적으로 진행한다.

우선순위:

1. `process_name`
2. `executable_path`
3. `display_name`

권장 정책:

- 같은 `process_name`이면 같은 앱 후보로 본다.
- `executable_path`가 둘 다 있고 서로 다르면 충돌 후보로 본다.
- 충돌 후보는 자동 병합하지 않고 후속 UI 또는 로그에서 검토 대상으로 둔다.
- 백업에만 있는 앱 또는 현재 DB에만 있는 앱은 기준 DB에 새 앱으로 추가할 수 있다.
- 새로 추가된 앱의 분류 출처는 `import`로 둘 수 있다.

주의:

- 같은 프로세스명이지만 다른 앱일 수 있다.
- 실행 파일 경로는 설치 위치 변경, portable 앱, 업데이트로 달라질 수 있다.
- 사용자 별칭은 표시용 정보이므로 앱 식별의 1차 기준으로 쓰지 않는다.

---

## 5. 분류 매칭 정책

분류는 앱보다 사용자의 의도가 강하게 들어갈 수 있으므로 더 조심스럽게 다룬다.

기본 분류:

- canonical name 기준으로 매칭한다.
- 색상 차이는 기준 DB의 값을 우선한다.
- 기본 분류는 삭제되지 않는 시스템 분류로 취급한다.

사용자 분류:

- 이름이 같으면 같은 분류 후보로 본다.
- 이름은 같지만 색상이나 의미가 다를 수 있으므로, 자동 병합은 보수적으로 처리한다.
- 충돌 시 기준 DB의 분류를 우선하고 가져온 앱은 기준 DB 분류에 연결한다.
- 기준 DB에 없는 사용자 분류를 추가할지, 미분류로 둘지는 후속 정책 또는 UI에서 선택할 수 있게 한다.

권장 1차 구현:

- 기본 분류는 canonical name 매칭
- 사용자 분류는 이름 기준 매칭
- 기준 DB에 없는 사용자 분류는 새 분류로 추가하되 `import` 출처를 남긴다.
- 사용자가 직접 지정한 `user` 출처 분류는 자동 덮어쓰기하지 않는다.

---

## 6. 설정 병합 정책

설정은 복원 방식별로 다르게 처리한다.

백업 기준 복원 + 이후 기록 보존:

- 백업 설정을 기준으로 유지한다.
- 현재 DB에서 가져온 기록 때문에 현재 설정을 덮어쓰지 않는다.
- Windows 시작 프로그램, 언어, 성능 진단 표시처럼 현재 PC 환경에 강하게 묶인 설정은 사용자가 다시 확인할 수 있게 안내한다.

현재 데이터 기준 가져오기:

- 현재 설정을 유지한다.
- 백업 설정은 가져오지 않는다.
- 백업 설정을 비교 표시하는 기능은 후속으로 둔다.

---

## 7. 기록 병합 정책

1차 대상 테이블:

- `foreground_sessions`
- `idle_sessions`
- `app_runtime_sessions`
- `process_runtime_sessions`
- `system_events`

권장 정책:

- 겹치지 않는 구간만 가져온다.
- 겹치는 구간은 기준 DB의 기록을 우선하고 candidate 기록은 제외한다.
- 앱/프로세스 기준이 있는 테이블은 앱 매칭 결과를 통해 새 `app_id`로 변환한다.
- `system_events`는 앱 ID가 없으므로 시간 구간 또는 이벤트 시각 기준으로 보수적으로 중복을 판단한다.

주의:

- foreground와 idle은 같은 시간대에 서로 다른 의미로 겹칠 수 있다.
- process runtime은 백그라운드 추적 설정에 따라 기록 밀도가 다르다.
- app runtime은 TimePilot 자체 실행 세션이므로 병합 후 기록 커버리지 분석에 영향을 줄 수 있다.

---

## 8. 사용자에게 보여줄 정보

병합 복원을 적용하기 전에 사용자는 다음을 알아야 한다.

- 가져올 수 있는 기록 수
- 겹쳐서 제외될 기록 수
- 새로 추가될 앱 수
- 새로 추가될 사용자 분류 수
- 충돌 후보 앱 수
- 안전 백업 생성 여부

현재 구현된 상세 분석 버튼은 기록 구간 기준의 보존 가능/가져오기 가능 수를 보여주는 1차 미리보기다.

앱/분류 추가 수와 충돌 후보 수는 후속 분석에서 확장한다.

---

## 9. 안전 규칙

- 병합 복원 전에는 안전 백업 생성을 권장한다.
- 기본 동작은 현재 데이터 손실 가능성이 가장 낮은 쪽이어야 한다.
- 자동 병합이 애매한 앱과 분류는 조용히 덮어쓰지 않는다.
- 사용자 직접 지정 분류는 자동 변경하지 않는다.
- 병합 결과는 완료 메시지 또는 로그에서 요약한다.

---

## 10. 구현 순서

1. 구간 비교 로직을 순수 서비스로 유지한다.
2. 백업 DB와 현재 DB를 임시 스냅샷으로 열어 상세 분석한다.
3. 앱 매칭 결과 모델을 추가한다.
4. 분류 매칭 결과 모델을 추가한다.
5. 병합 계획 객체를 만든다.
6. 병합 계획 미리보기 UI를 추가한다.
7. 안전 백업 후 병합 적용을 구현한다.
8. 병합 결과 요약을 표시한다.

---

## 11. 남은 결정 사항

- 사용자 분류 충돌 시 새 이름을 자동 생성할지 여부
- `system_events`의 중복 판단 기준
- 병합 복원에서 설정 비교 화면이 필요한지 여부
- 충돌 후보를 사용자에게 선택하게 할지, 1차에서는 제외할지 여부
- 여러 PC에서 같은 앱이 다른 경로에 설치된 경우의 처리
